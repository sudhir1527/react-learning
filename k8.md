# Kubernetes Service Accounts — Quick Notes

## 1. What Is a Service Account?
- **User accounts** are for humans (administrators, developers).
- **Service accounts** are for applications and automation, such as dashboards, monitoring tools, and CI/CD systems.
- A service account lets a workload authenticate to the Kubernetes API. **Permissions are controlled separately** through Kubernetes authorization/RBAC.

## 2. Essential Commands

```bash
# Create a service account
kubectl create serviceaccount dashboard-sa

# List service accounts
kubectl get serviceaccounts

# Inspect a service account
kubectl describe serviceaccount dashboard-sa

# Generate a time-limited token
kubectl create token dashboard-sa
```

## 3. Use a Service Account in a Pod

If `serviceAccountName` is omitted, the Pod uses the namespace's `default` service account.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  serviceAccountName: dashboard-sa
  containers:
    - name: my-app
      image: my-app
```

- Recreate the Pod to change its service account; an existing Pod's service account cannot be changed.
- To disable automatic token mounting:

```yaml
spec:
  automountServiceAccountToken: false
```

## 4. Token Mounting and Kubernetes Versions
- Traditionally, Kubernetes automatically created a Secret containing a long-lived service-account token.
- **Kubernetes 1.22:** moved toward bound, time-limited tokens requested through the TokenRequest API and mounted as projected volumes.
- **Kubernetes 1.24:** creating a service account no longer automatically creates a token Secret.
- `kubectl create token dashboard-sa` generates a time-limited token; its validity can be configured.
- Legacy, Secret-based tokens can be created manually, but long-lived tokens are less secure and should generally be avoided.

## 5. Token Location Inside a Pod
When automatic mounting is enabled, the token is typically available at:

```text
/var/run/secrets/kubernetes.io/serviceaccount/token
```

The mounted service-account files are usually read-only. Treat tokens as credentials and do not expose or log them.

## Key Takeaways
- Use a dedicated service account for each workload where practical.
- Grant only the permissions the workload needs using RBAC.
- Disable token mounting when the workload does not need Kubernetes API access.
- Prefer short-lived, automatically managed tokens over legacy long-lived Secret tokens.
